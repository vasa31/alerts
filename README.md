# Monitor — мониторинг складов и пожарных датчиков

Система из **FastAPI + SQLite + JWT** и **React UI (Vite)**.  
На карте два склада, в каждом по 3 датчика (температура, кислород, дым).  
Добавлять склады и датчики через UI нельзя — они задаются при старте.

## Вход и роли

Единый экран **Monitor** → логин. Дальше маршруты разные.

| Логин | Пароль | Роль | Куда попадёт |
|-------|--------|------|----------------|
| `duty` | `duty` | дежурный | `/duty` — пульт |
| `admin` | `admin` | администратор | `/admin` — кабинет |

### Пульт дежурного (`duty`)

- Карта: **два больших склада**, датчики **внутри** каждого
- Ползунки по каждому датчику — имитация показаний в реальном времени (значения уходят на бэкенд)
- Чекбокс **offline** — датчик серый, «не работает»
- Статус зоны и таймер наблюдения
- Уведомления и журнал событий
- Кнопки:
  - **Обновить** — перечитать карту/события
  - **Пожар был** / **Ложное** — закрыть открытое событие после выезда
  - **Окно прошло** — демо-кнопка (см. ниже)

### Кабинет администратора (`admin`)

- Та же карта (просмотр)
- Показания датчиков без ползунков
- Статистика: сигналы пожара, подтверждённые, ложные, доля ложных %
- Вызовы в пожарную и журнал событий

## Карта и цвета

На экране два склада рядом (А слева, Б справа). Датчики нарисованы **внутри** пола склада.

| Цвет | Статус | Смысл |
|------|--------|--------|
| зелёный | `ok` | норма |
| серый | `offline` | датчик не работает |
| красный (мигает) | `alarm` | тревога по порогу |

Подпись на карте: **имя + значение + статус** (не координаты).

---

## Логика пожара (1 / 2 / 3)

На зоне всегда 3 датчика: температура, кислород, дым.

| Сколько в `alarm` | Результат |
|-------------------|-----------|
| **1 из 3** | Ложное срабатывание. Уведомление дежурному (`soft`). В пожарную **не** шлём. |
| **2 из 3** | **Окно наблюдения**. Таймер, в пожарную пока не шлём. |
| **3 из 3** | Сразу **пожар** (`sharp`) + уведомление `fire_dept`. |

### Окно наблюдения (при 2 из 3)

1. Система засекает время (`CONFIRM_SECONDS` в `app/logic.py`).
2. Если за окно датчики **затихли** (0 или 1) → **пожара нет**.
3. Если после окна всё ещё **2+** в тревоге → **пожар** + вызов в пожарную.
4. Если во время окна сработал **третий** → сразу пожар.

В демо окно = **15 секунд**. На реальном складе поставьте `CONFIRM_SECONDS = 300` (5 минут).

Зачем: один датчик часто врёт; два коротких всплеска могут сами пройти; три сразу или два, которые не гаснут — уже пожар.

### Кнопка «Окно прошло»

Это **ускорение демо**, не обязательная кнопка на смене.

1. Поднимите ползунками **2 датчика** в тревогу → статус зоны `watch`.
2. Нажмите **Окно прошло** → бэкенд считает, что время окна уже вышло (`POST /api/watch/check?force=true`).
3. Если 2+ всё ещё в тревоге → будет **пожар** и уведомление пожарной.

Альтернатива: просто подождать 15 секунд и нажать **Обновить**.

Если до конца окна вернуть ползунки в норму — пожара не будет (кнопка не нужна).

### После выезда

Дежурный закрывает событие:

- **Пожар был** → `confirmed_fire`
- **Ложное** → `confirmed_false`

Это попадает в `/api/stats` (сравнение со старым протоколом).

## Как проверить сценарии (duty)

1. Войти: `duty` / `duty`.
2. **Один** ползунок за порог → один красный, ложное уведомление.
3. **Два** ползунка за порог → `watch`, таймер.
   - вернуть в норму → пожара нет;  
   - или «Окно прошло» / ждать 15 с → пожар.
4. **Три** в тревоге (кислород **вниз** ниже 18, температура и дым **вверх**) → сразу пожар.
5. Offline на одном датчике → серый + уведомление «проверьте датчик».
6. **Пожар был** / **Ложное** — закрыть событие.
7. Войти как `admin` — посмотреть статистику и вызовы пожарной.

Пороги:

| Тип | Тревога если |
|-----|----------------|
| temperature | value **>** 60 |
| oxygen | value **<** 18 |
| smoke | value **>** 50 |

Склад А: `192.168.1.11` / `.12` / `.13`  
Склад Б: `192.168.1.21` / `.22` / `.23`

## Протокол датчика (бэкенд)

Датчик шлёт HTTP POST (JWT **не** нужен):

```bash
curl -X POST http://127.0.0.1:8000/api/ingest/192.168.1.11 \
  -H "Content-Type: application/json" \
  -d '{"value": 90, "online": true}'
```

```json
{ "value": 72.5, "online": true }
```

| Поле | Смысл |
|------|--------|
| `value` | °C / O₂ % / уровень дыма |
| `online` | `false` → статус offline (серый) |

Ползунки на фронте вызывают тот же `/api/ingest/{ip}` — дальше работает та же бизнес-логика.

## JWT (для API / Swagger)

```bash
curl -s -X POST http://127.0.0.1:8000/api/login \
  -H "Content-Type: application/json" \
  -d '{"username":"duty","password":"duty"}'
```

В ответе `access_token` → в Swagger кнопка **Authorize** (BearerAuth) или заголовок:

```text
Authorization: Bearer <token>
```

Токен живёт 12 часов.

В Swagger разделы:

1. Авторизация  
2. Карта и склады  
3. Протокол датчиков  
4. Наблюдение и пожар  
5. Уведомления  
6. События  
7. Статистика  
8. Служебное

## API (кратко)

| Метод | Путь | Кто | Описание |
|-------|------|-----|----------|
| POST | `/api/login` | все | логин → JWT |
| GET | `/api/me` | JWT | текущий пользователь |
| GET | `/api/map` | JWT | карта, зоны, таймер, датчики |
| GET | `/api/sensors` | JWT | список датчиков |
| GET | `/api/warehouses` | JWT | склады |
| POST | `/api/ingest/{ip}` | датчик | показание (без JWT) |
| POST | `/api/sensors/{id}/reading` | датчик | показание по id |
| GET | `/api/notifications` | JWT | уведомления (`?target=duty\|fire_dept`) |
| GET | `/api/events` | JWT | журнал |
| POST | `/api/events/{id}/resolve` | duty/admin | `confirmed_fire` / `confirmed_false` |
| POST | `/api/watch/check?force=true` | JWT | пересчёт окна (= кнопка «Окно прошло») |
| GET | `/api/stats` | JWT | ложные vs подтверждённые |

## Что в БД (`fire_monitor.db`)

| Таблица | Содержание |
|---------|------------|
| `users` | логин, пароль, роль |
| `warehouses` | склады и координаты |
| `zones` | зоны + `watch_started_at` |
| `sensors` | тип, IP, порог, статус, значение, координаты |
| `events` | ложное / наблюдение / пожар / offline, решение |
| `notifications` | сообщения duty / fire_dept |

JWT в БД не хранится. При смене схемы таблиц удалите `fire_monitor.db` и перезапустите API.
